# Decisions

Dated log of judgment calls. Newest at the bottom. Anything here can be reversed by the human at a phase gate.

## 2026-09-28 — Pre-start

- **Runtime host.** Production (hourly ingest, DuckDB store, FastAPI/MCP server, hourly cron) runs on the existing OVH VPS, not the laptop. Reason: the user wants no dependence on their device, and revision capture requires a poller that is always up. Deployment rules are in CLAUDE.md. Phase 6's "deploy on the VPS" moves earlier for the poller alone.
- **Replay leak caveat (accepted by human 2026-09-28).** EIA serves only the latest value of each data point; there is no vintage API. Backfilled history therefore has a single `observed_at` (ingest time) and cannot support leak-free replay as the spec assumes. Proposed handling: (a) store the real ingest time; (b) for replay, derive a synthetic `observed_at = valid_time + series.lag_hours` for rows whose only known vintage is the backfill; (c) mark such rows `vintage = synthetic` so `revision.diff` and H0 report "no revision history" rather than "no revisions"; (d) state in the benchmark README that historical replay sees revised data, and that revision-based evidence is only available for cases opened after live polling started. The Phase 4 re-check test ("H0 refuted, H2 confirmed") will pass trivially on history; note it as such.
- **Benchmark honesty.** Fault generators are derived from the hypothesis templates, so the synthetic top-1 score partly measures self-agreement. Report synthetic and real-replay scores separately; the 5 real events are the headline.
- **Price data coverage (open).** H2/H3/H4 and `price.co_movement` depend on historical LMP via gridstatus. Coverage for 2020–2024 events is unverified; check before Phase 2 locks the templates.
- **Timezones.** Store and count rows in UTC. Convert to local time only for local-hour comparisons the spec states in CT (e.g. the Uri fuel bridge). EIA `region-data` is requested with `frequency=hourly` in UTC.
- **Weekly baseline refit.** To keep tools pure in `(inputs, as_of)`, the refit date is derived from `as_of` (most recent Monday 00:00 UTC ≤ as_of), never from the wall clock.
- **Routing.** Per the user's global policy, mechanical implementation from a fixed spec is delegated to Codex and verified here; design, data-correctness and anything touching secrets stays with Claude.

## 2026-09-28 — Phase 0 (ground-truth gate)

- **Time basis.** All API calls use `frequency=hourly`, which EIA serves in UTC; parquet `period` is tz-aware UTC. The 216-hour window is 2021-02-13T00Z..2021-02-21T23Z. The spec's "CT" instants (fuel bridge at 12:00 CT, "peak on 2021-02-15") are evaluated in US/Central (CST, UTC−6); the 02-15 peak is taken over UTC hours whose Central date is 02-15.
- **Result summary.** 216/216 hours for D, DF, NG, TI (no gaps). Peak DF−NG on 02-15 CT = 29,650 MW at 20:00 CT (DF 73,149 vs NG 43,499). Fuel bridge 02-14 12:00 → 02-15 12:00 CT: total −16,354 MW; NG −8,236 (50%), WND −4,974, COL −3,249, NUC −1,354; SUN +1,446. TI range −1,197..+357 MW. This is the current (revised) EIA view of the event, not the vintage that was visible during the storm; see the replay-leak entry above.
- **Missing hours.** None occurred, so the "≤ 4 missing, each listed in the report" rule is implemented but untested against real gaps. Missing hours would be reindexed to the 216-slot grid and listed as `YYYY-MM-DDTHH` (UTC) in the coverage table.
- **Served-load citation.** No EIA page states in plain words that D is "served load" during outages. The report cites (a) Form EIA-930 DATA DEFINITIONS, which define D as "actual demand" reported by the BA with no allowance for curtailed load, and (b) *Today in Energy* 2021-02-19 (id=46836) for the rotating outages starting midnight Feb 15. The `gridmonitor/about` URL is not a valid page and is not cited. The "≈20 GW peak load shed" and "until 02-18" figures are from ERCOT's public statements, not from EIA; treat them as context, not evidence.
- **Caching and idempotency.** Raw responses (`rows` array only, no request metadata, no key) are cached at `data/raw/uri_2021/{D,DF,NG,TI,fuel}.json` and reused on rerun, so the exit test runs offline after the first pull. Delete the JSON to force a refetch. `data/` is gitignored; a fresh clone must run the script once with a key.
- **Rate limiting.** 0.25 s minimum spacing between requests; 429/5xx and transport errors back off 2^n s up to 5 attempts. Only 5 requests are needed for this window; paging at 5,000 rows is implemented but not exercised.
- **Duplicates.** `drop_duplicates` on `(period[, fueltype])` keeps the first row. None were observed.
- **Test scope.** The exit test reads artifacts only; it does not call the API. Interpreted "216 hourly rows exist" as a 216-slot grid with ≤ 4 nulls, not literally 216 non-null rows.
- **Fuel-type categories.** February 2021 rows use the pre-2024 codes (COL, NG, NUC, OIL, OTH, SUN, WAT, WND); no BAT rows. Category mapping is deferred to the Phase 2 ontology as the spec requires.
- **Static analysis.** ruff (E,F,I,UP,B,SIM, line 100) and mypy --strict pass. pandas-stubs makes `idxmax`/`sum` return `Hashable`/`complex`; worked around with explicit numpy conversions rather than `# type: ignore`.
- **Routing.** Written inline rather than via Codex: the script reads the secret and is the data-correctness gate for the whole project.

## 2026-09-28 — Phase 1 (bitemporal data layer)

- **Two time columns, not one.** `observations` carries `observed_at` (when this process really received the value; audit truth) and `available_at` (what `as_of` filters on). Live rows: `available_at = observed_at`, `vintage = observed`. Backfilled rows: `available_at = min(valid_time + series.lag_hours, observed_at)`, `vintage = synthetic`. This is the accepted replay-leak handling; `vintage` lets tools say "no revision history" instead of "no revisions".
- **Append on change only.** A rerun writes a row only if the key is new or the value differs from the latest known value (`IS DISTINCT FROM`). A changed value for an existing key is a genuine revision seen now, so it is forced to `observed`/`observed_at` even in backfill mode. Verified on real data: 2 days of EIA (4,848 rows) then 0 on rerun.
- **Naive UTC `TIMESTAMP`, TimeZone pinned to UTC on every connection.** DuckDB's `TIMESTAMPTZ` needs pytz to read back into Python and is sensitive to session zone; naive UTC is deterministic. Pydantic validators convert aware inputs.
- **`as_of` is a DuckDB table macro** (`as_of(t)`) using `QUALIFY row_number()` with ties on `available_at` broken by later `observed_at`. Python wrapper `store.db.as_of(conn, t, ...)` is the only read path tools will use.
- **Series lags** (hours, set `available_at` for backfill): D 1, DF −14 (published ~10:00 ET prior day), NG/TI/fuel 24, interchange 48, sub-BA 36, Open-Meteo archive 120, DA LMP −12. These are estimates from the spec's cadence table, not measured; live polling will let us measure them later.
- **EIA hourly history starts 2019-01-01 for ERCO**, not 2018-07-01 as the spec says; backfill requests from 2018-07-01 and takes what comes. The live exit test measures expected hours from each series' first row rather than a fixed start.
- **Exit test split.** Property/idempotency/revision/429 tests run offline against fixtures (`tests/fixtures/eia/*.json`, 24 h of ERCO Uri data) with `httpx.MockTransport`. The full backfill count check is `@pytest.mark.live`, skipped unless `GRIDCASE_LIVE=1`; it is meant for the VPS. Rationale: a network-bound multi-hour test does not belong in a loop that runs until green.
- **Raw cache layout** is `data/raw/{source}/{route}/{key}_{start}_{end}.json` per request window, not `{date}.json` as the spec sketches: one date spans several routes and regions. Open-Meteo archive windows are cached only when older than 7 days (ERA5 finalisation).
- **gridstatus is an optional extra** (`uv sync --extra gridstatus`, pinned 0.36.0; ~40 transitive packages). Smoke test on 2023-05-01: fail-soft path works (run status `partial`, errors recorded, 0 rows) but no ISO returned day-ahead hub LMP: ERCOT/CAISO scrapers returned nothing for that date and PJM needs a free `PJM_API_KEY`. Real-time hourly is not offered by gridstatus for these ISOs, so v1 pulls day-ahead only. **Open for the Phase 2 gate:** LMP coverage for the five replay events is unverified; H2/H3/H4 price tests must tolerate "no data".
- **Entity ids**: BAs `ERCO/CISO/PJM/US48`; sub-BAs `BA/SUB`; fuels `BA/CODE` with raw EIA codes (canonical mapping is Phase 2); interchange paths `FROM->TO`; weather zones `wz/city`; hubs `BA/HUB`. 137 entities seeded from `ontology/entities.yaml`.
- **Process model for the VPS** (deferred to deployment): ingest and server must not both hold the DuckDB file open for writing. Plan: server opens read-only and reconnects per request; ingest is a short-lived timer job.
- **Routing.** Written inline: store semantics are the project's correctness core, and the source adapters were small enough that delegation overhead exceeded the work.

## 2026-09-28 — Phase 2 (semantic layer, ontology, hypothesis templates)

- **Compiler design (fresh, no Gen-2 notes).** `MetricQuery -> resolve -> plan -> emit`. Each metric becomes a CTE over `as_of(TIMESTAMP '<as_of>')` with every literal embedded (no bind parameters), so a receipt's `sql` is self-contained and re-executable. Kinds: `series` (one store series, optional `fuel`/`subregion` dimension), `aggregate` (mean/sum over the BA's weather zones or hubs), `derived` (arithmetic over other metrics via a tiny parsed expression language, joined on time), `rolling_ratio` (numerator ÷ trailing-window max, window function). Derived metrics may not depend on dimensioned metrics in v1. Sixteen metrics: the spec's fifteen plus `demand_by_subregion`, which `contribution.subregion` needs.
- **`balance_residual = D − (NG − TI)`, not the spec's `D − NG − TI`.** Measured on 2023-05-01..08: mean |D − NG + TI|/D is 0.00% for ERCO and PJM, 0.7% for US48, while the spec's sign gives 0.6%, 6.8% and 2.5%. EIA's TI is positive for net export, so `D = NG − TI`. `REVIEW:` confirm you are happy with the corrected identity; CISO shows a 4% residual even with the right sign (its EIA-930 books do not close as cleanly), so the ±3% exit check is asserted for ERCO only as the spec says.
- **Determinism bug found by the property test.** DuckDB's parallel `avg`/`sum` change floating-point summation order between runs; `temp_load_center` differed in the last bits. Fixed twice over: aggregates use `agg(value ORDER BY entity_id)` and every store connection sets `threads = 1`. Receipts must be byte-identical; this is cheap for our query sizes.
- **Fuel-category versioning** is data (`ontology/fuel_categories.yaml`): raw code → canonical fuel with `valid_from`. Canonical set: coal, geothermal, hydro, natural_gas, nuclear, other, petroleum, solar, storage, wind. BAT/PS/UES/OES → `storage`; SNB → `solar`; WNB → `wind`; UNK → `other`. Codes introduced in the 2024 Q3 schema change are valid from 2024-07-01. `REVIEW:` folding hybrid solar+battery (SNB) into solar overstates solar slightly after 2024; alternative is a separate `hybrid` fuel.
- **Weather zones.** US48's `served_by` is all 14 zones (an unweighted mean for now; the spec's population weighting is deferred until the temperature term in the baseline model needs it, Phase 3).
- **HDD/CDD** are computed hourly as `max(0, 18.3 − T)/24` (and the mirror) so the daily grain sums to degree-days; `daily_agg` is declared per metric.
- **Hypothesis templates (`ontology/hypotheses.yaml`).** Eight mechanisms in the spec's order, each with ordered tool tests and a falsifier in a small three-valued DSL (`tool.output.field op value`, `and/or/not`, no eval). Unknown outputs evaluate to *unknown*, never to *refuted*. `REVIEW:` this is the section the spec calls the highest-leverage hour; the wording, test order and thresholds (e.g. H2 refuted when top fuel < 50% of the drop, H5 < 60%, H0 revision < 5%) are mine. The output field names are contracts Phase 3 tools must honour.
- **Priors (`ontology/priors.yaml`).** Beta priors with ~10 pseudo-observations, defaults per template and (BA, season) overrides (e.g. H1 ERCO summer 0.6, H2 ERCO winter 0.35). `REVIEW:` values are judgment, not measured; case memory updates them from Phase 4.
- **Tool registry is a stub**: ten names with Pydantic input models; bodies are Phase 3.
- **Open for the Phase 2 gate: LMP coverage.** Still unverified per replay event (gridstatus returned nothing for 2023-05-01 DA on ERCOT/CAISO; PJM needs a key). `scripts/check_lmp_coverage.py` is scheduled with the `price.co_movement` tool in Phase 3. All price-based falsifier terms are written so that missing data leaves the hypothesis *unknown* rather than refuted.

## 2026-09-28 — Phase 3 (deterministic tools and evidence ledger)

- **Receipt identity** = sha256 of canonical JSON of (tool, inputs, as_of, output), 24 hex chars. `runtime_ms` and the SQL log are excluded so timing noise never changes an id. Outputs are rounded to 6 decimals and NaN/inf become null so receipts are byte-stable across runs.
- **Audited SQL.** Every query a tool runs (governed metric SQL from the compiler, or the two raw vintage queries in `revision.diff`) is logged in the receipt with a hash of the rows returned; the exit test re-executes each and compares hashes. This is the spec's "re-executed SQL reproduces the output" check made precise.
- **`data_version` is max `available_at`** of the rows read, not max `observed_at`: for backfilled history observed_at is the ingest clock (2026), which says nothing about what was knowable at as_of.
- **Baseline model**: hour-of-week dummies (168) + heating/cooling degree-hours of the BA's load-centre temperature, least squares on the trailing 3 years before the refit date = Monday 00:00 UTC ≤ as_of. Sigma per hour-of-week bucket is a MAD scale with a floor of 0.5% of mean |value| (so a perfectly regular synthetic series does not produce infinite z). No on-disk fit cache yet: fits take well under a second on the fixture. `REVIEW:` the temperature term is linear per side of 18.3 °C; the Uri fit shows ERCOT's true cold sensitivity is much steeper than a mild-winter training set can learn (136 MW/°C); three full winters on the VPS will help but a piecewise term may be needed.
- **Anomaly rule** as spec: |z| > 3 for ≥ 2 consecutive hours. `missing_hours` counts only *knowable* hours (valid_time + lag ≤ as_of); not-yet-published hours are not gaps. On real data the tool flagged a 6 GW evening miss on Sunday 2023-05-07 that the spec's "normal week" did not anticipate; the exit test's calm window is 2023-05-01..04 and the finding stands as a real forecast miss.
- **`contribution.subregion`**: EIA publishes no sub-BA forecast, so the miss is proxied by each subregion's change in mean demand vs the preceding 7 days; shares are additive by construction.
- **`regress.temperature`** returns three things: in-window slope/R² of demand on degree-hours; `share_explained` = R² of the forecast error on the *thermal surprise* (degree-hours beyond the prior-14-day same-hour climatology, a stand-in for the forecast-weather error we do not store) with `sign_consistent` (weather misses have the right sign: more extreme → more load; load shed has the wrong sign); and `implied_minus_actual_mw` from the multi-year baseline evaluated at the window's temperatures (a 28-day fit could not extrapolate Uri's cold and said demand was *above* implied).
- **`bridge.fuel`** has two modes. `level` (spec) is blind during load shed, when generation tracks served load and same-hour totals barely move; `expected` compares each fuel to its own baseline at the gap hour. Shares are of gross movement so they stay in [0, 1] when fuels offset.
- **`revision.diff`** reports `history: synthetic_only` when every row's vintage is synthetic, so "no revisions" is never claimed on backfilled data.
- **`price.co_movement`** answers `has_data: false` honestly; caps are 5,000 $/MWh (ERCOT) and 2,000 (others) with cap hours at ≥ 90%.
- **Fixture store** now holds ERCO-only training history (region data, sub-BA, fuel and temperature) for 2020-02..2021-02 and 2022-05..2023-07 (fuel from 2020-11 and 2023-02), 6.4 MB committed. Weather rows were re-stamped to a 1 h synthetic lag (`scripts/restamp_synthetic_vintage.py`, see Phase 4).

## 2026-09-28 — Phase 4 (planner, validator, executor, explainer, actions, memory)

- **Spec deviation, information state.** `REVIEW:` The spec expects H2 on top at as_of 2021-02-15T12:00Z. EIA publishes generation a day late; at 12:00Z on the 15th the fuel collapse (from ~07:00Z) was not in EIA-930, and at the first knowable gap hour (2021-02-15 11:00Z) gas was still at its expected 33 GW. A leak-free replay cannot know what was not published. The exit test asserts H2 on top at 2021-02-16T12:00Z, when the day-15 data has landed, and at 02-15T12:00Z only that H2 and H4 are not refuted. `bench/replay/uri_2021.yaml` uses 02-16T12:00Z as the case's as_of.
- **Weather vintage.** Open-Meteo's archive lags ~5 days (ERA5), which had made temperature unknowable for every replay. Observed temperature is live data in reality (airport METARs), so the synthetic lag for `om.*` is 1 h. Existing rows were re-stamped with `scripts/restamp_synthetic_vintage.py`; run it on the VPS after backfill. This is a metadata correction of synthetic vintages, not a value change.
- **"Insufficient" evidence.** A tool whose lagged series cannot yet reach the event (`anomaly.detect` when the knowable horizon ends before the run holding the worst hour; `bridge.fuel` when t1 precedes the event) sets `insufficient: true`; the executor withholds those outputs from falsifiers, so a hypothesis stays *open* rather than being refuted by pre-event hours. Unknown ≠ refuted, throughout.
- **Falsifier margins and confidence.** margin = signed, threshold-scaled distance of the falsifier from truth (fuzzy and = min, or = max), clipped to ±2; zero thresholds carry sign only. confidence = sigmoid(logit(prior) + margin + 0.5·log(coverage)) where coverage is the share of the miss the mechanism's `explains` field can account for (floor 2%). Untested hypotheses sit at their prior. `REVIEW:` the earlier K=2/clip 3 gave any "far from refuted" mechanism 0.98 regardless of prior; H3 (imports pinned at ERCOT's 1.2 GW ties) topped Uri on that basis.
- **Causal precedence in the ontology.** Templates carry `consequence_of` (H3 ← H2; H4 ← H2, H3). A supported consequence ranks right after its last supported cause. This is what puts H2 above H4 at 02-16T12Z: both are supported, load shed is the response to the shortfall. `REVIEW:` this edge is the single most opinionated line in the ontology.
- **H1 and H2 falsifiers changed from the Phase 2 wording.** H1 is refuted when the error moves the *wrong way* with the thermal surprise (Uri: colder yet less served load) or when the surprise explains little and peers do not co-move. H2 is refuted when the supply gap (DF − NG, a new governed metric) is not anomalous or generation sits at/above each fuel's expected output; fuel attribution is reported, not required, because it lags the gap by a publication day. H0 lost its redundant anomaly step (identity already counts missing hours). This keeps all eight templates inside the 12-step budget with shared steps.
- **Executor semantics.** Topological order; a step whose hypotheses are all refuted is skipped; a failing tool fails only its step. Falsifiers read the outputs of the steps that test that hypothesis; when two such steps share a tool (H6's wind and solar proxies) numeric fields merge by largest magnitude.
- **Default plan** (fallback and FakeLLM): H0 first, then templates greedily by prior and fewest new steps; identical (tool, inputs) steps are shared. All eight fit in 12 steps for a BA with a hub. Validator codes: E_NO_H0, E_H0_NOT_FIRST, E_TOO_FEW_HYP, E_UNKNOWN_TOOL, E_UNKNOWN_HYPOTHESIS, E_UNKNOWN_ENTITY, E_CYCLE, E_BAD_DEPENDENCY, E_OVER_BUDGET, E_DUP_STEP, E_UNFALSIFIABLE, E_STEP_HYPOTHESIS.
- **Explainer.** A template explainer writes one claim per receipt from fixed sentences whose numbers come from the receipt; it is the FakeLLM's explainer and the fallback when the model call fails. The verifier compares magnitudes (prose drops signs), treats shares as percentages, ignores dates/times, and forces uncited claims to `inferred`. The served-load caveat from CLAUDE.md is attached whenever H4 is not refuted.
- **LLM.** `AnthropicLLM` uses `messages.parse` with the Pydantic schema as `output_format`; model from `GRIDCASE_PLANNER_MODEL` (default `claude-opus-5`), cheap model `claude-sonnet-5`; tokens and cost logged per call. Plan ≤ 3 attempts then template default; explain 1 call; the re-check makes none. No live run yet (no API key on this machine).
- **Memory.** Learned priors live in a `learned_priors` table overlaying `priors.yaml` (Beta-Binomial: confirmed a+1, refuted b+1), never by rewriting the YAML. Repeated dev replays inflated H3's prior on the laptop; the benchmark must run on scratch memory (Phase 5).
- **Action.** `publish_case` is the one allow-listed action; dry-run by default; it always schedules a re-check task at as_of + max lag of the series used (floor 24 h) in `scheduled_tasks`.
- **Re-check verdicts.** refuted if the falsifier is true at the new as_of; confirmed if false; superseded if it was the top hypothesis and no longer is; open if unknown. On synthetic vintages the "H0 refuted" verdict is trivially available (no revisions can appear); noted per the Phase 1 decision.

## 2026-09-28 — Phase 5 (benchmark)

- **What the benchmark measures.** Three suites: 5 documented replay events (the independent signal), 25 synthetic cases per generator × 8 generators, and 100 clean windows for false alarms. Every case runs on its own scratch store copied from a base snapshot, with no learned priors and an empty ledger, so the score is of the system *without* memory. Failures are scored as misses, never raised. The offline exit test runs a reduced suite on the committed fixture; the full 5 + 300 run is `live` on the VPS. Results land in `bench/results/{date}_{model}[_novalidator].json`; `python -m gridcase.bench.readme` regenerates `bench/README.md` byte-stably.
- **Scratch stores are fabricated** by editing values in place; the append-only rule applies to the production store, not to a benchmark scratch. Reproducibility is asserted on a canonical row digest (md5 over sorted rows), not the DuckDB file bytes, which carry non-semantic headers.
- **Generators respect the identity and the publication lags.** Every fault keeps D = NG − TI (H2: fuel, NG and D fall together; H3: the extra import serves extra load; H4/H5: generation follows load with fuels scaled evenly) and ends 26 h (38 h for sub-BA) before as_of so the touched series are knowable. H6 leaves totals unchanged and moves wind into gas. H7 inflates the forecast on a real holiday.
- **Detectability floors (`REVIEW:` these are the parameter ranges the spec asks you to approve).** Weather shifts, fuel losses, shed load and zonal bumps are floored at 12% of load; the H1 shift grows *with* the sensitivity so temperature and demand stay coupled. Reason: the demand baseline's day-to-day error on ERCOT is several GW, so a 3–4 GW fault is inside the noise of the model that has to find it; a benchmark of faults at that scale would measure baseline error, not investigation. The floors mean the published synthetic score is "root-cause accuracy on events ≥ 12% of load".
- **Ground truth for H2/H4.** From EIA data alone, shed load without a fleet shortfall is not identifiable (energy balance forces generation down with served load), so the H4 generator's truth is [H4, H2] and the system's answer, by the causal edge, is H2 first: H4 scores top-3, not top-1, by construction. `REVIEW:` either accept that ceiling or re-label the H4 generator as [H2, H4].
- **H6 has low recall by design of the data.** Load-centre wind speed explains ~30% of ERCOT wind output (R² 0.31 with a cubic wind term); the proxy's residual scale is ~0.24 of capacity factor, so even a 90% loss of wind reaches |z| ≈ 2. The template keeps strict thresholds (no false positives on natural wind swings) and reports the bridge; an ISO wind/solar forecast (gridstatus offers ERCOT's) would make this sharp. Deferred to a later phase.
- **Template changes from Phase 4, all found by the benchmark:** H2/H4 now ask whether the miss is *weather-explained* (share × sign, sign-aware) rather than trusting our baseline's temperature extrapolation, keep the served-load significance as a mean-over-event z (unknown on runs shorter than 6 h), and H4 is refuted when demand moves with the weather. `contribution.subregion` scores redistribution of load share (positive part, with a 2% materiality floor) because week-over-week levels are weather-confounded. The baseline treats federal holidays as Sundays. The detector reports the event as the cluster of flagged runs (gaps < 6 h) holding the worst hour, and both start and end feed the tools.
- **Ranking tiers:** a supported H0 pre-empts everything; then supported mechanisms that cover ≥ 30% of the miss; then thinly supported and untested ones by confidence (untested at their prior); refuted last. Coverage weight is 1.0 (explaining a tenth of the miss costs ~2.3 logits): ERCOT's routinely maxed 1.2 GW ties no longer outrank a 20 GW shortfall. A consequence defers to its cause only when the cause is supported *and* substantial.
- **Offline numbers on the fixture (3 seeds per generator, FakeLLM, ERCO only):** top-1 14/24, top-3 19/24. Perfect on H0, H1, H5 and (2/3) H3, H7; H2 1/3 (two cases refuted by baseline bias on the day: the injected 12% loss landed on a day when natural demand ran that much above the baseline); H4 0/3 top-1 by the ceiling above; H6 0/3. These are the honest numbers for a system whose only expectation models are a mild-history hour-of-week baseline and four city temperatures; the VPS run with three winters is expected to move H2. The spec's 70% / 10% targets are placeholders for you to set; the phase is complete either way.
- **Price evidence.** `scripts/check_lmp_coverage.py` shows gridstatus returns no day-ahead hub LMP for Uri (and nothing for the other events once the hub bug in the script was fixed). All price clauses evaluate to unknown, never to refuted. PJM would need a free `PJM_API_KEY`.
- **Replay cases** are drafted in `bench/replay/*.yaml` with sources; Uri's as_of is 2021-02-16T12:00Z (Phase 4 decision) and the eclipse is a hard negative (`expect_flagged: false`). On the laptop only Uri and the June 2023 heat dome have data; the other three are recorded as failures, which is what the exit test checks.

## 2026-09-28 — Phase 6 (MCP server, web UI, deployment)

- **Process model (closes the Phase 1 open question).** DuckDB allows one writer process per file, so the server *is* the writer: `gridcase serve` opens the store once, hands out cursors, and runs the hourly live ingest and the re-check drain in one background thread (`--ingest-interval 3600`, `--drain-interval 600`). `deploy/install.sh` installs the server unit and stops the ingest timer; `deploy/install.sh timer` is the inverse for an ingest-only host. Exactly one of the two is ever enabled. The units set no environment; `.env` in the working directory is the only source of secrets.
- **MCP.** `mcp` SDK 2.2 `MCPServer`, stateless Streamable HTTP, JSON responses, registered as a Starlette *route* at `/mcp` (a Mount only matches `/mcp/...`; the bare path fell through to the static-files mount and answered 405, caught by `tests/unit/test_server.py`). Tools: `list_open_cases`, `get_case`, `investigate(entity, metric, as_of, token)` → `{task_id}`, `get_task(task_id)`, `tool_<name>` for each Phase 3 tool (read-only, no case, no ledger write), `bench_summary`. The SDK ships no Tasks-extension server support, so the task handle is an ordinary tool result polled through `get_task`, which is what the 2026-07-28 spec prescribes for a stateless server anyway; the re-check is not a second task but the drained `scheduled_tasks` row. ## 2026-09-29 — Hard rule 6 changed: evidence-only question box

- **User decision.** Visitors should be able to ask what a page shows and why, answered from "the content structured the same way the model gets to make its own decisions, so it is accurate". Rule 6 ("no chat UI") existed to stop GridCase becoming a chatbot that talks past its evidence; the question box keeps evidence central, so the rule is rewritten rather than broken: answers come only from the case's causes, falsifiers, plan, evidence and follow-up (or the scorecard's results), every sentence is verified against evidence like the conclusion, and uncited sentences are marked interpretation or dropped.

## 2026-09-29 — Detector calibration Part A (branch `feat/detector-calibration-a`)

- **What changed.** `anomaly.detect` now reports, per hour, `exceedance` = |z| / `threshold_z` and whether the hour is `in_alarm`; the receipt adds `max_exceedance`, `threshold_z`, `threshold_n` and keeps `z`/`max_abs_z` so older cases stay comparable. The threshold is fitted with the baseline (`baseline.py::_threshold`), leak-free under the Monday refit rule. An alarm is a run of >= 3 exceeding hours, or a run holding one hour above 2x the threshold. Knobs are a new governed config, `ontology/detector.yaml` (per-BA overrides allowed, none set).
- **Departure from the plan's statistic.** The plan said "99.5th percentile of hourly |residual|". On the fixture, with Winter Storm Uri inside the 3-year training window, that quantile rose from 5.5 to ~8 sigmas and the alarm missed 13 of 17 injected faults. The threshold is instead the **95th percentile of each training day's worst |z|**, never below 3: a multi-day storm is a handful of days out of ~1,000 and sits inside the discarded 5%. On identical synthetic data a four-day 30-sigma storm moved the hourly q99.5 by +214% and the daily-max q95 by +1% (`test_a_multi_day_storm_in_training_barely_moves_the_threshold`). The per-hour-of-week MAD sigma still carries the daily shape; only the multiple is calibrated.
- **Placeholders.** Training hours whose forecast error is exactly 0 (EIA's CAISO placeholder: demand first published equal to the forecast) are excluded from the threshold sample (`threshold_n` counts the hours used). They are *not* excluded from the detector's input: a placeholder hour has zero error and cannot raise an alarm; its only effect is on the H0 missing-hours count, left for the Part A review.
- **Templates.** H2 and H6 now read `anomaly.detect.max_exceedance < 1` where they read `max_abs_z < 3`; H3's "well inside its range" reads `max_exceedance < 0.67` (two thirds of the calibrated bar, which is >= 2 sigmas as before) instead of `max_abs_z < 2`. H0's `identity.balance.max_abs_z` is a different tool and unchanged.
- **Test changed, with reason.** `test_anomaly_needs_two_consecutive_hours` encoded the old rule (a lone hour never alarms). The new rule alarms on a lone catastrophic hour, so it became `test_anomaly_alarms_on_a_single_catastrophic_hour` (a 20 GW lone miss against a perfect synthetic forecast now alarms); a lone *moderate* hour not alarming is covered on noisy data in `tests/unit/test_detector.py`.
- **Pre-existing bug fixed.** The baseline fit cache was keyed on `id(conn)` and the observation row count. Connection ids are reused after close and benchmark scratch stores are edited in place with the same row count, so a stale fit could be served (it surfaced as a flaky test). The cache is now keyed on a digest of the training rows the fit actually reads, plus the detector config; the training queries always run, so receipts log them either way.
- **Fixture benchmark (reduced suite: 3 per generator, 12 null windows, ERCO, FakeLLM).**

  | detector | false alarms | faults alarmed | synthetic top-1 | top-3 | replay top-1 |
  |---|---|---|---|---|---|
  | main (3 sigma, 2 h) | 2/12 | 17/24 | 54% | 79% | 2/5 |
  | daily-max q0.95, 3 h (committed default) | **0/12** | 11/24 | 50% | 71% | 2/5 |
  | daily-max q0.90, 3 h | 2/12 | 14/24 | 54% | 79% | 2/5 |

  Uri (H2) and the June 2023 heat (H1) stay correct in every configuration; the other three replay events have no laptop data.
- **`REVIEW:` the honest trade-off.** At the 12%-of-load fault floor, injected faults move ERCOT's forecast error by about 4–5 sigmas, which is where a bad but ordinary day sits (calibrated k ≈ 4.2–4.5 on the fixture). The old detector caught those faults only by also alarming on 24% of the VPS's quiet windows. Twelve fixture null windows cannot pick the setting. **Tune on the VPS** per the plan: run the full suite at `daily_max_quantile` 0.95 and 0.90 on seed 1, choose, then evaluate the chosen value on seed 2 and the replay events. Part B (judging weather against the operator's forecast) is what should recover the lost top-1, because it stops "weather" from absorbing faults on days the baseline already under-predicts.
